\begin{abstract}
Speculative decoding accelerates autoregressive language-model inference by separating a fast draft role from a stronger verification role. The algorithmic literature usually focuses on acceptance rules and model quality, while production systems also inherit a lower-level scheduling question: must every draft/verify boundary become a host-visible wait? We study this question with a reproducible CUDA artifact that isolates launch overhead, role handoff, and GPU-resident scheduling. The benchmark compares a serial two-phase stream baseline, a host-synchronized two-kernel baseline, and a fused single-kernel design that partitions resident warps into draft and validator roles. On an NVIDIA RTX 5070 Ti, the fused path reduces median latency by \(1.56\times\) relative to the host-synchronized two-kernel path for the minimal benchmark scope. It does not beat the serial stream baseline in the same aggregate, and repeated trials show substantial variance. We therefore present the result as systems evidence for an execution mechanism: host-visible waiting is a policy choice that can be moved into GPU-resident synchronization, but fusion must be balanced against resource pressure and workload shape.
\end{abstract}

\section{Introduction}
Speculative decoding has become a central technique for reducing the latency of large language model (LLM) generation. A draft computation proposes one or more future tokens, and a verifier checks those proposals against a stronger target computation while preserving output quality or distributional constraints \cite{leviathan2023speculative,chen2023accelerating,cai2024medusa}. This decomposition is usually described as an algorithmic optimization, but it also imposes a concrete execution schedule: draft work, handoff, verify work, and a decision about whether the next step can proceed.

In a full serving stack, that schedule passes through batching policy, kernel launches, CUDA streams, key-value (KV) cache management, and host-side control paths \cite{kwon2023pagedattention,yu2022orca,nvidiaTensorRTLLM,nvidiaFasterTransformer}. The visible latency of speculative decoding can therefore include waits that are not inherent to the algorithm. A host fence between draft and verify kernels is simple and modular, but it can be expensive when the per-step kernels are short. Conversely, fusing roles into one launch can remove orchestration overhead but increase register pressure, reduce occupancy, and make memory handoff more delicate.

This paper studies the execution-system question in isolation: if draft and verify roles are mapped onto heterogeneous warp groups inside one GPU kernel, how much host-visible waiting can be removed, and what trade-offs appear? The repository is intentionally not a vLLM, TensorRT-LLM, FasterTransformer, or Triton integration \cite{kwon2023pagedattention,nvidiaTensorRTLLM,nvidiaFasterTransformer}. It is a kernel-level systems artifact designed to make scheduling claims auditable. Every reported path has a corresponding CUDA implementation, NVTX range, CSV output, and profiling workflow.

The contributions are:
\begin{enumerate}[leftmargin=1.5em]
  \item A CUDA microbenchmark suite for speculative-decoding-style scheduling, comparing serial stream execution, host-synchronized two-kernel execution, and fused warp-specialized execution.
  \item A fused draft/verify kernel design that uses intra-kernel role partitioning and shared-memory handoff to replace host-visible fences with GPU-resident synchronization.
  \item Memory and cluster variants that exercise KV-shaped prefetch, thread-block cluster sequencing, Tensor Memory Accelerator (TMA), and distributed shared memory (DSMEM) concepts on supported architectures \cite{nvidiaHopperGuide,nvidiaCudaGuide}.
  \item A reproducibility package containing CSV trials, Nsight Systems timeline guidance, figure workflows, and scope limits that distinguish kernel scheduling evidence from end-to-end serving claims.
\end{enumerate}

\section{Background}
\subsection{Speculative decoding}
Speculative decoding uses an inexpensive draft mechanism to propose future tokens and a stronger target model to verify them. Leviathan et al. introduced a sampling procedure that can preserve the target distribution while accelerating decoding by verifying multiple candidate tokens in parallel \cite{leviathan2023speculative}. Follow-on work has explored assisted generation, multi-token prediction heads, tree attention, and relaxed serving trade-offs \cite{chen2023accelerating,cai2024medusa}. These papers primarily define algorithmic opportunities; this work asks how the draft/verify boundary should be represented in the GPU execution schedule.

These methods shift some decoding work from a strictly serial loop to a draft/verify structure. The structure creates an opportunity for parallelism, but it also creates a scheduling boundary. If the verifier waits for draft results through host-mediated control, launch and synchronization costs can become visible. If the two roles remain resident on the GPU, the boundary can be represented by shared memory, barriers, and cluster-level sequencing instead.

\subsection{Serving systems and memory pressure}
LLM serving systems optimize a broader space than the one studied here: request batching, preemption, memory paging, KV-cache sharing, and scheduler fairness. Orca demonstrated iteration-level scheduling for transformer serving \cite{yu2022orca}, while vLLM's PagedAttention reduced KV-cache waste through a paging-inspired memory manager \cite{kwon2023pagedattention}. NVIDIA FasterTransformer and TensorRT-LLM represent the production-library side of the same design space, combining optimized kernels, quantization, batching, KV caching, and deployment integration \cite{nvidiaFasterTransformer,nvidiaTensorRTLLM}. Those systems motivate this work but also define its boundary. Waiting is a Choice does not implement a production serving memory manager, admission control, or multi-request policy. It isolates the GPU-side schedule that such systems could eventually target.

\subsection{GPU mechanisms}
Modern NVIDIA GPUs expose multiple mechanisms for moving synchronization closer to the data path. Cooperative groups and thread-block clusters allow communication and ordering beyond a single CTA. Hopper-class hardware introduced TMA and DSMEM features that support asynchronous tensor movement and cluster-local shared-memory access \cite{nvidiaHopperGuide,nvidiaCudaGuide}. Attention kernels such as FlashAttention show the importance of organizing transformer computation around on-chip storage and IO-aware tiling rather than treating GPU memory traffic as a secondary concern \cite{dao2022flashattention}. The artifact uses these features where available while retaining pre-cluster fallbacks so the central fused-vs-host-sync comparison remains portable across the development machines used for this work.

\section{Design}
\subsection{Execution alternatives}
The benchmark models three execution alternatives:
\begin{description}[leftmargin=1.5em]
  \item[Serial two-phase stream.] Draft-like and verify-like kernels are launched on one CUDA stream. Stream ordering carries the dependence without an explicit host synchronization between phases.
  \item[Two-kernel host sync.] Draft and verify work are split across launches with host-visible synchronization. This path models a conservative orchestration design where the CPU observes the boundary.
  \item[Fused single-kernel.] Draft and verify roles are assigned to resident warp groups inside one kernel. Shared memory is the handoff lane, and block-level synchronization orders producer and consumer phases.
\end{description}

The fused design is not mathematically different from draft/verify speculation. It is a different placement of the same boundary. The hypothesis is that moving the boundary from the host into a resident kernel removes avoidable launch and synchronization delay when the work per step is small enough for orchestration overhead to matter.

\subsection{Kernel paths}
The core implementation is \texttt{k\_fused\_pipeline}, which partitions block-resident warps into draft-side and verify-side roles. Static shared memory stores intermediate values, and synchronization establishes a deterministic handoff. The host-synchronized baseline keeps the same conceptual phases but exposes their boundary to the CPU. The serial stream baseline distinguishes fusion wins from the simpler benefit of avoiding a host fence.

The repository also includes three extensions that test whether the scheduling idea remains coherent under richer GPU behavior. First, \texttt{k\_kv\_tile\_pipeline} assigns warp groups to KV-shaped prefetch and compute work over double-buffered tiles, echoing the broader lesson from IO-aware attention kernels that useful speedups often come from reducing off-chip traffic and staging data deliberately \cite{dao2022flashattention}. Second, \texttt{k\_cluster\_tma\_dsmem\_kv} uses a two-block cluster, TMA bulk copies, DSMEM reads, and producer/consumer sequence numbers to avoid tile lapping. Third, WMMA paths exercise FP16/BF16 tensor-core style throughput kernels, while guarded FP8/FP4 paths mark architecture-toolkit combinations still under integration.

\subsection{Instrumentation}
All benchmark regions are wrapped in NVTX ranges with the \texttt{WIC:*} prefix when CUDA NVTX headers are available. Nsight Systems then shows the relative wall-clock shape of \texttt{WIC:serial\_two\_phase\_stream}, \texttt{WIC:two\_kernels\_host\_sync}, and \texttt{WIC:fused\_pipeline\_mixed\_float}. Nsight Compute is reserved for per-kernel resource analysis rather than headline latency, because profiler replay and counter collection can perturb timing.

\section{Experimental Protocol}
\subsection{Hardware and software}
The checked-in headline CSV was captured on an NVIDIA GeForce RTX 5070 Ti, reported by the benchmark as \texttt{sm\_120}-class hardware with CUDA runtime 13.0. The repository Dockerfile pins a CUDA 12.8.0 development container for reproducible builds; the recorded runtime field in the CSV reflects the host/runtime used for the current artifact. Build scripts default to \texttt{WIC\_CUDA\_ARCH=120} and allow overrides for other GPUs.

\subsection{Benchmark commands}
The headline minimal-scope run uses:
\begin{quote}
\small
\texttt{OUT=results/final\_bench.csv scripts/run\_microbench.sh --bench-scope minimal --skip-fused-correctness --iters 30 --warmup 5}
\end{quote}
For the reported aggregate, the minimal command was repeated for 10 trials and summarized in \texttt{results/benchmark\_summary.md}. Size-sweep artifacts were generated separately for \(n \in \{256,1024,2048\}\). Nsight Systems figures are captured with:
\begin{quote}
\small
\texttt{scripts/capture\_nsys.sh -- --bench-scope minimal --skip-correctness --iters 20 --warmup 3}
\end{quote}

\subsection{Metrics}
The primary scalar metric is latency in microseconds. For repeated trials we report median of trial means, mean of trial means, trial standard deviation, and p95 of trial means. This choice is intentionally conservative: it exposes instability in short GPU microbenchmarks instead of relying on a single favorable run. Throughput columns are present in CSV output but are zero for the minimal scheduling paths and are not used as headline metrics.

\section{Results}

Table~\ref{tab:headline} summarizes 10 minimal-scope trials at \(n=256\). The fused path is faster than the host-synchronized two-kernel path by \(14.5079 / 9.3185 = 1.56\times\) on median trial mean latency. The serial stream path remains faster than fused in this aggregate. The result supports a narrow claim: fusing draft/verify roles removes a host-synchronization penalty, but fusion is not automatically superior to all non-fused schedules.

\subsection{Size sweep}
Table~\ref{tab:size} reports single-run size sweeps. The trend is non-monotonic: at \(n=1024\), fused is faster than both two-kernel host sync and serial stream; at \(n=256\) and \(n=2048\), serial stream is faster than fused. This reinforces the resource trade-off expected from a heterogeneous kernel. Fusing roles can reduce launch overhead, but the extra live state and synchronization can dominate when problem size and launch geometry do not match the fused schedule.

\subsection{Resource status}
The repository includes an occupancy worksheet, but measured Nsight Compute register and occupancy entries are not yet committed. Consequently, this paper does not claim measured occupancy values. The design expectation is still clear: heterogeneous kernels carry draft and verify live state together, so register pressure and active-warp residency are likely limiting factors. The current artifact documents how to capture these counters and treats them as a readiness gate before stronger performance claims.

\section{Discussion}
The central lesson is that draft/verify waiting has more than one implementation. A host fence is an easy correctness boundary, but short speculative kernels can spend a meaningful fraction of their time in orchestration. A fused resident kernel can move that boundary to shared memory and barriers, producing lower median latency than a host-synchronized split in the current minimal benchmark.

The serial stream baseline is equally important. It prevents overclaiming by showing that ``one launch'' is not the only way to avoid host waits. CUDA stream ordering can already remove some CPU involvement while preserving modular kernels. The fused design is therefore most compelling when GPU-resident handoff enables additional overlap, locality, or scheduling decisions that stream-ordered kernels cannot express.

For systems builders, the artifact suggests a staged path. First, use kernel-level probes to identify whether host-visible draft/verify orchestration is significant. Second, evaluate whether fusion or persistent-kernel style scheduling improves the schedule without exhausting registers. Third, only then integrate with full serving concerns such as batching, KV-cache paging, and request-level fairness.

\section{Limitations}
The current artifact has several deliberate limits:
\begin{itemize}[leftmargin=1.5em]
  \item It is a microbenchmark suite, not an end-to-end LLM serving system.
  \item It does not model real token acceptance distributions, rollback costs, or quality metrics.
  \item It does not implement production KV-cache allocation, paging, eviction, or multi-request sharing.
  \item The size sweep is single-run per size and non-monotonic; stronger claims require repeated size sweeps and variance controls.
  \item Nsight Compute occupancy/register data is not populated in the checked-in worksheet.
  \item Some low-precision paths are guarded because FP4/FP8 support depends on architecture and toolkit maturity.
\end{itemize}

\section{Future Work}
Future work should connect this kernel evidence to a complete inference stack. Immediate engineering steps include repeated size sweeps, clock/power/environment capture, populated occupancy tables, ablations over warp-role ratios, and launch-bound tuning. Larger systems work includes integrating a fused or persistent draft/verify executor with batching schedulers and optimized inference runtimes, modeling stochastic acceptance and rollback, and evaluating interactions with KV-cache paging systems such as vLLM \cite{yu2022orca,kwon2023pagedattention,nvidiaTensorRTLLM}.
